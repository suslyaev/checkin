# UI-автотесты

UI-тесты запускаются только для постоянного окружения `testAnis`:

```text
http://62.113.111.146:8001
```

Защита в тестах запрещает запуск на другом сервере или порту. Тесты через UI
создают события, контакты и регистрации в постоянной базе `testAnis`.
Созданные записи после завершения тестов не удаляются.

Новые записи получают последовательные имена:

```text
Selenium Event 0001
Selenium Event 0002
Selenium Guest 0001
Selenium Guest 0002
```

Старые записи не изменяются. Тест находит максимальный существующий номер и
использует следующий. Запускайте тесты последовательно, без `pytest-xdist`,
чтобы два теста не выбрали одинаковый номер.

## Подготовка учётных данных

В текущем окне PowerShell укажите телефон суперпользователя `testAnis`:

```powershell
$env:E2E_PHONE="+79879631518"
```

Введите пароль скрыто. Пароль не добавляется в Git и не сохраняется в README:

```powershell
$secure = Read-Host -Prompt "Password" -AsSecureString
$env:E2E_PASSWORD = [Net.NetworkCredential]::new("", $secure).Password
```

## Запуск всех тестов

Запуск без отображения браузера:

```powershell
$env:E2E_HEADLESS="1"
$env:E2E_SLOWMO="0"
python -m pytest tests\e2e -v
```

Запуск с видимым браузером и паузой две секунды между поддерживаемыми
действиями:

```powershell
$env:E2E_HEADLESS="0"
$env:E2E_SLOWMO="2"
python -m pytest tests\e2e -v
```

Значение `E2E_SLOWMO` задаёт длительность учебной паузы в секундах. Для
обычного быстрого запуска используйте `0`.

## Список автотестов

Список отсортирован по имени файла, затем по имени теста.

### 1. Авторизация — `test_auth.py`

#### `test_user_can_log_in`

Проверяет успешный вход существующего суперпользователя `testAnis`.

Шаги:

1. Открывает страницу авторизации на порту `8001`.
2. Вводит телефон из `E2E_PHONE`.
3. Вводит пароль из `E2E_PASSWORD`.
4. Нажимает кнопку входа.
5. Ожидает загрузки корневого элемента React-приложения.

Ожидаемый результат: пользователь авторизован и видит основной интерфейс.
Тест не создаёт и не изменяет записи в базе.

#### `test_user_can_log_out`

Проверяет завершение пользовательской сессии через UI.

Шаги:

1. Авторизуется на стенде `testAnis`.
2. Открывает меню настроек в интерфейсе событий.
3. Нажимает «Выйти».
4. Ожидает возвращения формы авторизации.

Ожидаемый результат: сессия завершена, снова отображается страница входа.
Тест не создаёт и не изменяет записи в базе.

#### `test_user_stays_on_login_page_with_wrong_password`

Проверяет отказ в авторизации с неправильным паролем.

Шаги:

1. Открывает страницу авторизации.
2. Вводит правильный телефон и заведомо неправильный пароль.
3. Отправляет форму.
4. Проверяет, что форма входа осталась на странице.

Ожидаемый результат: вход не выполнен, пользователь не получает доступ к
приложению. Тест не изменяет данные в базе.

### 2. Check-in — `test_checkin.py`

#### `test_checker_can_confirm_guest`

Проверяет полный сценарий регистрации и подтверждения прихода гостя.

Подготовка через UI:

1. Авторизуется как суперпользователь `testAnis`.
2. Создаёт новое событие `Selenium Event NNNN`.
3. Создаёт нового гостя `Selenium Guest NNNN`.
4. Добавляет гостя в событие.
5. Последовательно переводит регистрацию в статус `registered`.

Основная проверка:

1. Открывает check-in список созданного события.
2. Нажимает кнопку подтверждения напротив гостя.
3. Проверяет текст уведомления «Подтверждено».
4. Проверяет, что гость исчез из очереди ожидающих check-in.

Ожидаемый результат: статус регистрации меняется с `registered` на `visited`.
Событие, гость и результат check-in остаются в постоянной базе.

#### `test_checker_can_find_guest_by_last_name`

Проверяет поиск зарегистрированного гостя в конкретном событии.

Подготовка через UI:

1. Создаёт новое нумерованное событие.
2. Создаёт нового нумерованного гостя.
3. Добавляет гостя в событие со статусом `registered`.

Основная проверка:

1. Открывает check-in список события.
2. Вводит фамилию гостя в поле поиска.
3. Отправляет поисковую форму.
4. Проверяет отображение полного имени гостя.

Ожидаемый результат: поиск возвращает гостя, созданного для этого события.
Созданные событие, контакт и регистрация остаются в постоянной базе.

### 3. События — `test_event.py`

#### `test_admin_can_create_event_through_ui`

Проверяет создание события через настоящую форму Django Admin.

Шаги:

1. Авторизуется как суперпользователь.
2. Открывает форму добавления мероприятия.
3. Определяет следующий свободный порядковый номер.
4. Заполняет название `Selenium Event NNNN`.
5. Указывает тестовый адрес, время начала и время окончания.
6. Включает видимость события.
7. Сохраняет форму.
8. Проверяет получение числового ID и корректный формат названия.

Ожидаемый результат: новое видимое событие создано через UI и остаётся в
постоянной базе `testAnis`.

## Запуск отдельных сценариев

Создание события через Django Admin:

```powershell
python -m pytest tests\e2e\test_event.py -v
```

Поиск гостя в созданном событии:

```powershell
python -m pytest tests\e2e\test_checkin.py::test_checker_can_find_guest_by_last_name -v
```

Подтверждение check-in гостя:

```powershell
python -m pytest tests\e2e\test_checkin.py::test_checker_can_confirm_guest -v
```

Проверка успешного входа:

```powershell
python -m pytest tests\e2e\test_auth.py::test_user_can_log_in -v
```

## Завершение работы

После тестов удалите логин и пароль из текущей сессии PowerShell:

```powershell
Remove-Item Env:E2E_PHONE -ErrorAction SilentlyContinue
Remove-Item Env:E2E_PASSWORD -ErrorAction SilentlyContinue
```

Сообщения Chrome про GPU, USB или GCM обычно не связаны с результатом теста.
Ориентируйтесь на итоговый статус pytest: `PASSED`, `FAILED` или `ERROR`.
